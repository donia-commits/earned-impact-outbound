1. Executive Summary

This document defines Version 1 of Earned Impact's BigQuery Data Warehouse — the internal engineering specification for how prospect, activity, and performance data is structured, stored, and moved across the outbound technology stack. It is written for engineering and operations use, not for client presentation.

Purpose: as Earned Impact's outbound department scales from one internal build to a repeatable, multi-client operating system, every tool in the stack — the dialer, the CRM, enrichment providers, and reporting — needs one shared, trustworthy data layer underneath it. This document defines that layer.

Why BigQuery exists: today, prospect and activity data is split across ReadyMode, GoHighLevel, spreadsheets, and enrichment tools, each with its own partial view. Without a central warehouse, list building, suppression, and reporting all depend on manual reconciliation between systems — which does not scale past a single account, let alone a portfolio of clients.

Why BigQuery is the Source of Truth

Every operational system (ReadyMode, GoHighLevel) is a consumer or contributor to BigQuery — never the authority on its own. If a number in a dashboard, a suppression list, or a contact record is ever in question, BigQuery is the only place the answer should be looked up. This single rule is what makes the system auditable, and what makes it possible to replicate cleanly for every future client.

High-level architecture: enrichment and list sources (Apollo, FullEnrich, CSV/Sheets imports) feed contact and company records into BigQuery. BigQuery pushes calling lists out to ReadyMode IQ; ReadyMode pushes call outcomes and dispositions back in. Qualified contacts and booked meetings flow from BigQuery into GoHighLevel; meeting outcomes and pipeline changes sync back. All reporting — for Earned Impact leadership and, eventually, for clients — is generated directly from BigQuery, never from a point tool. Gemini sits alongside the warehouse as an AI enrichment and qualification aid, not as a system of record.

This is a v1 specification. It is intentionally scoped to the current single-client implementation (Earned Impact) while every naming convention, schema decision, and data-flow rule below is written to hold up unchanged when a second client (e.g. TriChad) is added. Section 8 lists what is deliberately out of scope for this version.

The current outbound technology stack, and the role each platform plays relative to the warehouse:

These are named in Section 8 (Future Expansion) only — they are not architected here, and no schema decisions below should assume their presence.

3. Database Architecture

Each table below is defined with its purpose, keys, recommended columns, relationships to other tables, and a operational best practice. Field lists are the recommended v1 column set — engineering may add columns as needed, but should not remove or rename the fields marked as required without updating this specification.

3.1 Companies

Stores the organization-level record for every prospect account — the anchor that contacts, campaigns, and reporting roll up to.

Primary Key: company_id    Foreign Keys: client_id

ColumnTypeDescription
company_idSTRINGUnique identifier (required). Generated at ingestion, never reused.
client_idSTRINGWhich Earned Impact client this record belongs to (required for multi-client support).
nameSTRINGLegal or commonly-used organization name.
domainSTRINGPrimary website domain — used as a natural dedupe key alongside name.
industrySTRINGVertical / org type, e.g. higher-ed, mental health, trade org.
org_sizeSTRINGBucketed size, e.g. by budget or headcount, per the client's ICP definition.
source_systemSTRINGWhere the record originated (Apollo, CSV, manual, etc.) — required for auditability.
created_at / updated_atTIMESTAMPStandard audit timestamps on every table (see Section 7).

Relationships: One-to-many with Contacts (a company has multiple contacts) and with Campaigns (a company can be targeted across multiple campaigns over time).

Best Practice: Deduplicate on domain + normalized name before insert, not after. A messy Companies table is the single most common source of bad suppression logic downstream.

3.2 Contacts

The individual prospect record — the level at which calls, emails, and meetings actually happen.

Primary Key: contact_id    Foreign Keys: company_id

ColumnTypeDescription
contact_idSTRINGUnique identifier (required).
company_idSTRINGLinks to the parent Companies record.
full_nameSTRINGContact's name.
titleSTRINGJob title — used for buyer-persona segmentation.
emailSTRINGPrimary email, ideally FullEnrich-verified.
phoneSTRINGPrimary dialable number.
linkedin_urlSTRINGProfile URL, if available.
contact_statusSTRINGLifecycle status: new, enriched, in_sequence, dnc, converted, etc.
source_systemSTRINGOrigin of the record (Apollo, CSV, manual, referral).

Relationships: Many-to-one with Companies. One-to-many with Calls, Email/LinkedIn Activity, and Meetings.

Best Practice: contact_status should be a controlled vocabulary (see Section 7), not free text — it is the field suppression logic and reporting will filter on most often.

3.3 Campaigns

The container for a specific outbound push — a defined audience, offer, and time window for one client.

Primary Key: campaign_id    Foreign Keys: client_id

ColumnTypeDescription
campaign_idSTRINGUnique identifier (required).
client_idSTRINGOwning client — critical for multi-client rollout.
nameSTRINGHuman-readable campaign name.
channel_mixSTRINGWhich channels are active: calls, email, LinkedIn, SMS (future).
statusSTRINGplanning, active, paused, complete.
start_date / end_dateDATEPlanned or actual campaign window.
offer_idSTRINGReference to the offer/messaging variant being tested, if applicable.

Relationships: One-to-many with Sequences, Calls, and Reporting Metrics. Many-to-one with the owning client.

Best Practice: Never reuse a campaign_id across a re-launch — version it (e.g. suffix -v2) so historical reporting stays accurate.

3.4 Sequences

Defines the ordered set of touches (call, email, LinkedIn steps) that make up a campaign's outreach cadence.

Primary Key: sequence_id    Foreign Keys: campaign_id

ColumnTypeDescription
sequence_idSTRINGUnique identifier (required).
campaign_idSTRINGParent campaign.
step_orderINTEGERPosition of this step within the cadence.
channelSTRINGcall, email, linkedin, sms (future).
template_refSTRINGPointer to the script/template/asset used at this step.
wait_daysINTEGERDelay before this step fires relative to the previous one.

Relationships: Many-to-one with Campaigns. One-to-many with Email/LinkedIn Activity (each activity references the sequence step that generated it).

Best Practice: Keep templates themselves out of BigQuery (they belong in the asset/knowledge base); store only the reference so copy edits don't require warehouse changes.

3.5 Calls

One row per dial made through ReadyMode — the core unit of outbound activity for the calling channel.

Primary Key: call_id    Foreign Keys: contact_id, campaign_id, user_id

ColumnTypeDescription
call_idSTRINGUnique identifier, ideally ReadyMode's native call ID (required).
contact_idSTRINGWho was called.
campaign_idSTRINGWhich campaign this dial belongs to.
user_idSTRINGWhich SDR made the call.
call_timestampTIMESTAMPWhen the call occurred.
duration_secondsINTEGERTalk time.
recording_urlSTRINGLink to the call recording, if retained.

Relationships: Many-to-one with Contacts, Campaigns, and Users. One-to-one with Call Dispositions.

Best Practice: Load raw call events from ReadyMode on a fixed schedule (e.g. every 15–30 minutes) rather than real-time streaming for v1 — simpler to build and sufficient for current volume.

3.6 Call Dispositions

The outcome recorded against a call — what actually happened on the dial.

Primary Key: disposition_id    Foreign Keys: call_id

ColumnTypeDescription
disposition_idSTRINGUnique identifier (required).
call_idSTRINGThe call this outcome belongs to.
disposition_codeSTRINGControlled vocabulary, e.g. connected, voicemail, no_answer, wrong_number, dnc, meeting_booked.
notesSTRINGFree-text notes from the SDR.
dnc_flagBOOLEANTrue if the contact should be suppressed going forward.

Relationships: One-to-one with Calls. Feeds Meetings (when disposition_code = meeting_booked) and the suppress-list workflow.

Best Practice: This table is the trigger for the ReadyMode suppression loop: dnc_flag = true here should automatically add the contact to the export used to filter future upload files, per the workflow Donia and Yahia defined.

3.7 Meetings

A booked appointment resulting from outbound activity, and its ultimate outcome.

Primary Key: meeting_id    Foreign Keys: contact_id, disposition_id, user_id

ColumnTypeDescription
meeting_idSTRINGUnique identifier (required).
contact_idSTRINGWho the meeting is with.
disposition_idSTRINGThe call disposition that produced this meeting, if applicable.
user_idSTRINGSDR or account lead who booked/ran the meeting.
scheduled_atTIMESTAMPMeeting date/time.
outcomeSTRINGquick_no or closed_deal per Earned Impact's current definition of a successful appointment — extendable as a scored rubric later.
ghl_opportunity_idSTRINGLinked GoHighLevel opportunity/pipeline record.

Relationships: Many-to-one with Contacts, Call Dispositions, and Users. Feeds Reporting Metrics directly.

Best Practice: Keep outcome as a small controlled set now; do not let it silently expand into a longer pipeline-stage list — that belongs in GoHighLevel, referenced here by ghl_opportunity_id.

3.8 Users / SDRs

Everyone who touches outbound activity — SDRs, account leads, and managers.

Primary Key: user_id    Foreign Keys: —

ColumnTypeDescription
user_idSTRINGUnique identifier (required).
full_nameSTRINGDisplay name.
roleSTRINGSDR, account_lead, manager, etc.
teamSTRINGInternal team or client pod, once multi-client.
active_flagBOOLEANWhether this user is currently active — do not delete rows for departed staff.

Relationships: One-to-many with Calls and Meetings.

Best Practice: Never hard-delete a user record — historical Calls and Meetings must keep resolving to a name for reporting integrity even after someone leaves.

3.9 Email / LinkedIn Activity

One row per outbound touch on the email or LinkedIn channel — the equivalent of Calls for non-phone channels.

Primary Key: activity_id    Foreign Keys: contact_id, sequence_id

ColumnTypeDescription
activity_idSTRINGUnique identifier (required).
contact_idSTRINGWho was touched.
sequence_idSTRINGWhich sequence step generated this touch.
activity_typeSTRINGemail_sent, email_opened, email_replied, linkedin_connect, linkedin_message, etc.
activity_timestampTIMESTAMPWhen it occurred.
statusSTRINGsent, delivered, bounced, replied, failed.

Relationships: Many-to-one with Contacts and Sequences.

Best Practice: Design this table now even though cold email/LinkedIn automation is not launching yet (Section 8) — adding the table later after data has been flowing to Calls and Meetings only is a much larger migration than including it in v1.

3.10 Reporting Metrics

Pre-aggregated, dashboard-ready performance numbers — the only table reporting tools should query directly.

Primary Key: metric_id    Foreign Keys: campaign_id, client_id

ColumnTypeDescription
metric_idSTRINGUnique identifier (required).
campaign_idSTRINGWhich campaign this row summarizes.
client_idSTRINGOwning client.
metric_dateDATEThe day (or period) this row represents.
dialsINTEGERTotal dials for the period.
connectsINTEGERTotal connected calls.
meetings_bookedINTEGERMeetings resulting from the period.
dial_to_appointment_rateFLOATConnects/dials and dials/meeting ratios per the ~1–2 per 400 dials benchmark.

Relationships: Aggregates from Calls, Call Dispositions, and Meetings. Consumed by dashboards and client-facing reporting.

Best Practice: Compute this table on a schedule (e.g. nightly) rather than having dashboards aggregate raw Calls/Meetings on the fly — keeps dashboard load fast and gives one canonical definition of every KPI.

4. Data Relationships

The diagram below shows the core entity relationships described in Section 3: how a Company rolls up to its Contacts, how Contacts drive Calls and Activity, and how those roll up through Dispositions into Meetings and Reporting.

Read the diagram as: Companies → Contacts is one-to-many; Contacts branch out into Calls, Email/LinkedIn Activity, and (via Campaigns) Sequences; Calls resolve into Call Dispositions, which in turn produce Meetings; and Reporting Metrics aggregates across Campaigns and Meetings. Users attach to both Calls and Meetings to preserve SDR-level attribution.

5. Data Flow Architecture

Where Section 4 shows how the data is structured at rest, this diagram shows how it moves between systems in production.

Sourcing: Apollo, FullEnrich, and CSV/Sheets imports all write new or enriched Company and Contact records into BigQuery — none of them are queried directly by downstream systems.

Calling loop: BigQuery pushes contact lists to ReadyMode IQ; ReadyMode returns call outcomes and dispositions, which land back in BigQuery, closing the loop described in Section 3.6.

CRM loop: qualified contacts, booked meetings, and opportunities move from BigQuery into GoHighLevel; meeting outcomes and pipeline changes sync back into BigQuery, closing that loop as well.

Reporting: dashboards and reports are generated only from BigQuery's Reporting Metrics table (Section 3.10) — never directly from ReadyMode or GoHighLevel exports. Gemini sits alongside the flow as an AI assist for enrichment and qualification, reading context from BigQuery without owning any data of its own.

7. Naming Convention

A consistent naming standard is what makes this schema safely reusable across future clients without special-casing. All names use snake_case; all identifiers are prefixed for readability in a multi-client warehouse.

ElementConventionExample
Datasetclient_slug (one dataset per client, lowercase, underscores)earned_impact, trichad
Tablesnake_case, plural nouncontacts, call_dispositions
Columnsnake_case, descriptive, no abbreviations beyond this doc's setcontact_status, scheduled_at
Primary Key<entity>_id, STRING, generated at ingestioncontact_id, campaign_id
Foreign KeySame name as the referenced table's primary keycompany_id referenced in contacts
TimestampISO 8601, UTC, suffix _at for instants / _date for calendar datescreated_at, metric_date
Status valuesLowercase snake_case, from a controlled vocabulary per fieldin_sequence, meeting_booked, dnc
Disposition codesLowercase snake_case, fixed list maintained in this documentconnected, voicemail, wrong_number
Campaign ID<client_slug>-<year>-<sequence>, versioned on relaunchei-2026-01, ei-2026-01-v2
Client IDShort lowercase slug, matches the dataset nameearned_impact

Any new field, table, or status value proposed outside this list should be added here first, then implemented — this document is the control, not an after-the-fact description.

8. Future Expansion

The following are acknowledged as directional next steps. None are architected in this version — they are named here only so v1 design choices (Section 3, 7) don't accidentally foreclose them.

  • Cold Email platform integration — will extend the existing Email Activity table rather than requiring a new one.
  • LinkedIn Automation tooling — will extend the existing LinkedIn Activity rows already scoped in Section 3.9.
  • AI Agents — for qualification, enrichment, or first-touch outreach, layered on top of BigQuery as consumers, not new sources of truth.
  • SMS Automation — a new channel, following the same Sequences/Activity pattern used for email and LinkedIn.
  • Multi-client deployments — dataset-per-client structure (Section 7) is designed for this; TriChad is the next planned instance.
  • Revenue Attribution — connecting closed-deal revenue back through Meetings → Calls → original source, once client billing data is available in the warehouse.
Next Steps

Recommend engineering review of Sections 3 and 7 before first implementation, confirmation of the ReadyMode and GoHighLevel sync mechanisms (API vs. scheduled export) with the current tool licenses, and a short validation pass once Earned Impact's own outbound data starts flowing, before this spec is finalized as the standard template for TriChad and future clients.
