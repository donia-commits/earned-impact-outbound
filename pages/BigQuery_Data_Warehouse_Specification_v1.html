1. Executive Summary

This document defines Version 1 of Earned Impact's BigQuery Data Warehouse — the internal engineering specification for how prospect, activity, and performance data is structured, stored, and moved across the outbound technology stack. It is written for engineering and operations use, not for client presentation.

Purpose: as Earned Impact's outbound department scales from one internal build to a repeatable, multi-client operating system, every tool in the stack — the dialer, the CRM, enrichment providers, and reporting — needs one shared, trustworthy data layer underneath it. This document defines that layer.

Why BigQuery exists: today, prospect and activity data is split across ReadyMode, GoHighLevel, spreadsheets, and enrichment tools, each with its own partial view. Without a central warehouse, list building, suppression, and reporting all depend on manual reconciliation between systems — which does not scale past a single account, let alone a portfolio of clients.

Why BigQuery is the source of truth: every operational system (ReadyMode, GoHighLevel) is a consumer or contributor to BigQuery — never the authority on its own. If a number in a dashboard, a suppression list, or a contact record is ever in question, BigQuery is the only place the answer should be looked up.

High-level architecture: enrichment and list sources (Apollo, FullEnrich, CSV/Sheets imports) feed contact and company records into BigQuery. BigQuery pushes calling lists out to ReadyMode IQ; ReadyMode pushes call outcomes and dispositions back in. Qualified contacts and booked meetings flow from BigQuery into GoHighLevel; meeting outcomes and pipeline changes sync back. All reporting is generated directly from BigQuery, never from a point tool. Gemini sits alongside the warehouse as an AI enrichment and qualification aid, not as a system of record.

This is a v1 specification, scoped to the current single-client implementation (Earned Impact), written so every naming convention, schema decision, and data-flow rule holds up unchanged when a second client (e.g. TriChad) is added. Section 8 lists what is deliberately out of scope for this version.

3. Database Architecture

Each table is defined with its purpose, keys, recommended columns, relationships, and a best practice. Field lists are the recommended v1 column set.

3.1 Companies

Stores the organization-level record for every prospect account. Primary Key: company_id   Foreign Keys: client_id

ColumnTypeDescription
company_idSTRINGUnique identifier (required). Generated at ingestion, never reused.
client_idSTRINGWhich Earned Impact client this record belongs to (required for multi-client support).
nameSTRINGLegal or commonly-used organization name.
domainSTRINGPrimary website domain — used as a natural dedupe key alongside name.
industrySTRINGVertical / org type, e.g. higher-ed, mental health, trade org.
org_sizeSTRINGBucketed size, e.g. by budget or headcount, per the client's ICP definition.
source_systemSTRINGWhere the record originated (Apollo, CSV, manual, etc.) — required for auditability.
created_at / updated_atTIMESTAMPStandard audit timestamps on every table (see Section 7).

Relationships: one-to-many with Contacts and Campaigns. Best practice: deduplicate on domain + normalized name before insert, not after — a messy Companies table is the single most common source of bad suppression logic downstream.

3.2 Contacts

The individual prospect record — the level at which calls, emails, and meetings actually happen. Primary Key: contact_id   Foreign Keys: company_id

ColumnTypeDescription
contact_idSTRINGUnique identifier (required).
company_idSTRINGLinks to the parent Companies record.
full_nameSTRINGContact's name.
titleSTRINGJob title — used for buyer-persona segmentation.
emailSTRINGPrimary email, ideally FullEnrich-verified.
phoneSTRINGPrimary dialable number.
linkedin_urlSTRINGProfile URL, if available.
contact_statusSTRINGLifecycle status: new, enriched, in_sequence, dnc, converted, etc.
source_systemSTRINGOrigin of the record (Apollo, CSV, manual, referral).

Relationships: many-to-one with Companies; one-to-many with Calls, Email/LinkedIn Activity, and Meetings. Best practice: contact_status should be a controlled vocabulary, not free text.

3.3 Campaigns

The container for a specific outbound push — a defined audience, offer, and time window for one client. Primary Key: campaign_id   Foreign Keys: client_id

ColumnTypeDescription
campaign_idSTRINGUnique identifier (required).
client_idSTRINGOwning client — critical for multi-client rollout.
nameSTRINGHuman-readable campaign name.
channel_mixSTRINGWhich channels are active: calls, email, LinkedIn, SMS (future).
statusSTRINGplanning, active, paused, complete.
start_date / end_dateDATEPlanned or actual campaign window.
offer_idSTRINGReference to the offer/messaging variant being tested, if applicable.

Best practice: never reuse a campaign_id across a re-launch — version it (e.g. suffix -v2) so historical reporting stays accurate.

3.4 Sequences

Defines the ordered set of touches (call, email, LinkedIn steps) that make up a campaign's outreach cadence. Primary Key: sequence_id   Foreign Keys: campaign_id

ColumnTypeDescription
sequence_idSTRINGUnique identifier (required).
campaign_idSTRINGParent campaign.
step_orderINTEGERPosition of this step within the cadence.
channelSTRINGcall, email, linkedin, sms (future).
template_refSTRINGPointer to the script/template/asset used at this step.
wait_daysINTEGERDelay before this step fires relative to the previous one.

Best practice: keep templates themselves out of BigQuery (they belong in the asset/knowledge base); store only the reference so copy edits don't require warehouse changes.

3.5 Calls

One row per dial made through ReadyMode. Primary Key: call_id   Foreign Keys: contact_id, campaign_id, user_id

ColumnTypeDescription
call_idSTRINGUnique identifier, ideally ReadyMode's native call ID (required).
contact_idSTRINGWho was called.
campaign_idSTRINGWhich campaign this dial belongs to.
user_idSTRINGWhich SDR made the call.
call_timestampTIMESTAMPWhen the call occurred.
duration_secondsINTEGERTalk time.
recording_urlSTRINGLink to the call recording, if retained.

Best practice: load raw call events from ReadyMode on a fixed schedule (e.g. every 15–30 minutes) rather than real-time streaming for v1.

3.6 Call Dispositions

The outcome recorded against a call. Primary Key: disposition_id   Foreign Keys: call_id

ColumnTypeDescription
disposition_idSTRINGUnique identifier (required).
call_idSTRINGThe call this outcome belongs to.
disposition_codeSTRINGControlled vocabulary, e.g. connected, voicemail, no_answer, wrong_number, dnc, meeting_booked.
notesSTRINGFree-text notes from the SDR.
dnc_flagBOOLEANTrue if the contact should be suppressed going forward.

Best practice: this table is the trigger for the ReadyMode suppression loop — dnc_flag = true here should automatically add the contact to the export used to filter future upload files.

3.7 Meetings

A booked appointment resulting from outbound activity, and its ultimate outcome. Primary Key: meeting_id   Foreign Keys: contact_id, disposition_id, user_id

ColumnTypeDescription
meeting_idSTRINGUnique identifier (required).
contact_idSTRINGWho the meeting is with.
disposition_idSTRINGThe call disposition that produced this meeting, if applicable.
user_idSTRINGSDR or account lead who booked/ran the meeting.
scheduled_atTIMESTAMPMeeting date/time.
outcomeSTRINGquick_no or closed_deal per Earned Impact's current definition of a successful appointment.
ghl_opportunity_idSTRINGLinked GoHighLevel opportunity/pipeline record.

Best practice: keep outcome as a small controlled set now; the longer pipeline-stage list belongs in GoHighLevel, referenced here by ghl_opportunity_id.

3.8 Users / SDRs

Everyone who touches outbound activity. Primary Key: user_id

ColumnTypeDescription
user_idSTRINGUnique identifier (required).
full_nameSTRINGDisplay name.
roleSTRINGSDR, account_lead, manager, etc.
teamSTRINGInternal team or client pod, once multi-client.
active_flagBOOLEANWhether this user is currently active — do not delete rows for departed staff.

Best practice: never hard-delete a user record — historical Calls and Meetings must keep resolving to a name for reporting integrity even after someone leaves.

3.9 Email / LinkedIn Activity

One row per outbound touch on the email or LinkedIn channel. Primary Key: activity_id   Foreign Keys: contact_id, sequence_id

ColumnTypeDescription
activity_idSTRINGUnique identifier (required).
contact_idSTRINGWho was touched.
sequence_idSTRINGWhich sequence step generated this touch.
activity_typeSTRINGemail_sent, email_opened, email_replied, linkedin_connect, linkedin_message, etc.
activity_timestampTIMESTAMPWhen it occurred.
statusSTRINGsent, delivered, bounced, replied, failed.

Best practice: design this table now even though cold email/LinkedIn automation is not launching yet — adding it later after data has flowed to Calls and Meetings only is a much larger migration than including it in v1.

3.10 Reporting Metrics

Pre-aggregated, dashboard-ready performance numbers — the only table reporting tools should query directly. Primary Key: metric_id   Foreign Keys: campaign_id, client_id

ColumnTypeDescription
metric_idSTRINGUnique identifier (required).
campaign_idSTRINGWhich campaign this row summarizes.
client_idSTRINGOwning client.
metric_dateDATEThe day (or period) this row represents.
dialsINTEGERTotal dials for the period.
connectsINTEGERTotal connected calls.
meetings_bookedINTEGERMeetings resulting from the period.
dial_to_appointment_rateFLOATConnects/dials and dials/meeting ratios per the ~1–2 per 400 dials benchmark.

Best practice: compute this table on a schedule (e.g. nightly) rather than having dashboards aggregate raw Calls/Meetings on the fly.

4. Data Relationships

Companies → Contacts is one-to-many; Contacts branch out into Calls, Email/LinkedIn Activity, and (via Campaigns) Sequences; Calls resolve into Call Dispositions, which in turn produce Meetings; and Reporting Metrics aggregates across Campaigns and Meetings. Users attach to both Calls and Meetings to preserve SDR-level attribution.

5. Data Flow Architecture

Sourcing: Apollo, FullEnrich, and CSV/Sheets imports all write new or enriched Company and Contact records into BigQuery — none of them are queried directly by downstream systems.

Calling loop: BigQuery pushes contact lists to ReadyMode IQ; ReadyMode returns call outcomes and dispositions, which land back in BigQuery.

CRM loop: qualified contacts, booked meetings, and opportunities move from BigQuery into GoHighLevel; meeting outcomes and pipeline changes sync back into BigQuery.

Reporting: dashboards and reports are generated only from BigQuery's Reporting Metrics table — never directly from ReadyMode or GoHighLevel exports. Gemini sits alongside the flow as an AI assist for enrichment and qualification, reading context from BigQuery without owning any data of its own.

7. Naming Convention

All names use snake_case; all identifiers are prefixed for readability in a multi-client warehouse.

ElementConventionExample
Datasetclient_slug (one dataset per client, lowercase, underscores)earned_impact, trichad
Tablesnake_case, plural nouncontacts, call_dispositions
Columnsnake_case, descriptive, no abbreviations beyond this doc's setcontact_status, scheduled_at
Primary Key<entity>_id, STRING, generated at ingestioncontact_id, campaign_id
Foreign KeySame name as the referenced table's primary keycompany_id referenced in contacts
TimestampISO 8601, UTC, suffix _at for instants / _date for calendar datescreated_at, metric_date
Status valuesLowercase snake_case, from a controlled vocabulary per fieldin_sequence, meeting_booked, dnc
Disposition codesLowercase snake_case, fixed list maintained in this documentconnected, voicemail, wrong_number
Campaign ID<client_slug>-<year>-<sequence>, versioned on relaunchei-2026-01, ei-2026-01-v2
Client IDShort lowercase slug, matches the dataset nameearned_impact

Any new field, table, or status value proposed outside this list should be added here first, then implemented — this document is the control, not an after-the-fact description.

8. Future Expansion

Acknowledged as directional next steps. None are architected in this version — named here only so v1 design choices (Sections 3, 7) don't accidentally foreclose them.

  • Cold Email platform integration — will extend the existing Email Activity table rather than requiring a new one.
  • LinkedIn Automation tooling — will extend the existing LinkedIn Activity rows already scoped in Section 3.9.
  • AI Agents — for qualification, enrichment, or first-touch outreach, layered on top of BigQuery as consumers, not new sources of truth.
  • SMS Automation — a new channel, following the same Sequences/Activity pattern used for email and LinkedIn.
  • Multi-client deployments — dataset-per-client structure (Section 7) is designed for this; TriChad is the next planned instance.
  • Revenue Attribution — connecting closed-deal revenue back through Meetings → Calls → original source, once client billing data is available in the warehouse.

Next Steps
